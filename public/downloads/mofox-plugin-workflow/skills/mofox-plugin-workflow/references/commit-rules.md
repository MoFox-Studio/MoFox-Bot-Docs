# 插件提交与版本规则

本文件规定如何**起草和执行**插件提交。默认只在 Phase 6 提供建议；任何提交、版本递增、构建、推送和发布都必须分别得到用户确认。

## Commit 格式

提交标题统一使用：

```text
type(scope): subject
```

### type

只使用能准确描述变更目的的类型：

- `feat`：新增用户可见能力。
- `fix`：修复错误行为。
- `refactor`：不改变对外行为的重构。
- `perf`：性能改进。
- `test`：只改测试。
- `docs`：只改文档。
- `build`：依赖、打包或构建系统变更。
- `ci`：持续集成配置变更。
- `style`：只调整格式、空白或代码风格，不改变行为。
- `chore`：不属于以上类别的维护工作；不得用来掩盖功能或修复。
- `revert`：回退既有提交。

### scope

- 默认使用插件名，例如 `feat(todo_plugin): add recurring reminders`。
- 只改主仓插件基础设施时使用明确模块名，例如 `test(plugin-loader): ...`。
- 不使用含糊 scope（如 `misc`、`update`、`stuff`）。
- 一个提交跨多个无共同 scope 的插件，通常说明提交不原子，应拆分。

### subject

- 使用简洁、结果导向的短句，描述目的而非文件操作；中英文跟随目标仓库现有提交风格。
- 不写“update files”“fix issue”等无法独立理解的描述。
- 标题应能与实际 diff 对应，不夸大未实现能力。

### body

简单变更可以省略。需要时说明：

- 为什么要改；
- 关键行为、兼容性或迁移影响；
- 无法从 diff 直接看出的取舍。

不要在 body 中粘贴过程日志、测试流水或重复标题。

### footer

仅在确有需要时添加：

- 破坏性变更：`BREAKING CHANGE: <迁移说明>`；
- 关联事项：`Closes #123`、`Refs #123`；
- 项目明确要求的签署信息。

**按用户偏好，不自动添加 `Co-Authored-By`。** 只有用户明确要求且作者信息准确时才添加。

## 原子提交

- 每个提交只表达一个可独立审查、测试和回退的目的。
- 实现、对应测试和必要文档通常属于同一个原子功能提交。
- 无关格式化、顺手重构、多个插件的独立改动应拆开。
- 不创建空提交，不重复提交同一生成产物，不把密钥、环境文件或构建产物混入提交。
- 提交前核对完整 staged diff 和未跟踪文件；只暂存目标文件。

## 仓库归属

Phase 0 必须确定插件是否为独立 Git 仓库：

- **独立插件仓库**：插件源码、插件内测试、插件 README/CHANGELOG、插件 manifest 和插件版本提交到插件仓库。
- **主仓内插件**：插件源码及主仓 `test/plugins/<name>/` 测试提交到 Neo-MoFox 主仓。
- **主仓集成测试或框架配置**即使服务于独立插件，也归主仓；插件代码仍归插件仓库。
- 不把独立插件仓库当成主仓普通目录提交，也不从主仓提交其嵌套工作树内容。

若任务跨仓：

1. 分别检查每个仓库的状态和 diff；
2. 按仓库归属拆分提交，各自使用准确的标题；
3. 分别运行与该仓变更相关的验证；
4. 分别向用户展示建议提交，不用一个提交描述覆盖两个仓库；
5. 每个仓库的 commit 和 push 都单独确认。

## SemVer 与版本源同步

根据对外影响建议版本：

- `MAJOR`：破坏兼容的配置、命令、Service/API、数据格式或行为变更。
- `MINOR`：向后兼容的新功能、新组件或新配置能力。
- `PATCH`：向后兼容的修复、性能改进或不改变公开契约的维护。
- 仅文档/测试改动通常不要求插件版本递增，除非发布政策另有规定。
- 预发布版本继续使用现有预发布序列，不自行改换版本策略。

版本同步顺序：

1. 完成并验证代码、测试和必要文档；
2. 根据实际兼容性影响提出 SemVer 类型和目标版本；
3. 获得用户对版本递增的单独确认；
4. 更新所有版本源：至少 `manifest.json` 的 `version`、插件类 `plugin_version`，以及项目实际存在的包元数据、README/CHANGELOG 版本信息；
5. 再次检查版本源一致性并重跑必要验证；
6. 起草版本提交；获得用户对 commit 的单独确认后才提交；
7. 构建、push、`mpdt market package-update`、`mpdt market publish` 分别再次确认后才执行。

不得先 bump 再决定改动内容，也不得为了“准备发布”自动 build 或 publish。

## 发布动作确认边界

以下动作互不替代授权，必须逐项明确确认：

- `git commit`
- 任意版本递增命令或手工版本修改
- build/package
- `git push`
- `mpdt market package-update`
- `mpdt market publish`
- 其他创建 release、tag 或上传制品的动作

用户只批准“开发”“验证”或“准备上线”时，只能修改和测试，并在 Phase 6 起草版本与 commit 建议，不能执行上述动作。
