# 插件文档规则

文档是插件交付的一部分，但只在有真实读者和内容时创建。不要为了“目录完整”生成占位文件。

## 条件创建

- **README.md**：新插件默认创建；已有插件只在已有 README 或本次变更影响安装、配置、使用方式、组件行为、依赖或限制时更新。纯内部重构且用户行为不变时，不为凑交付项改 README。
- **CHANGELOG.md**：仅当插件仓库已经采用 changelog、用户明确要求维护发布历史，或当前任务本身是一次需要记录的版本发布时创建或更新。普通开发任务不新建空 CHANGELOG，也不预写“Unreleased”占位。
- **LICENSE**：仅在用户明确指定许可证，或独立插件仓库已有明确许可证政策时创建或修改。不得替用户猜选许可证。
- **配置示例**：仅在配置复杂、必须手写、包含需要解释的密钥占位符，或 README 片段不足以表达完整组合时创建 `config.example.toml` / `examples/config.toml`；不得复制真实配置或凭据。
- **API 文档**：仅当插件向其他插件暴露稳定 Service、提供 Router HTTP 接口、实现 Adapter 协议，或用户明确要求时创建；简单内部函数不单独生成 API 文档。
- **docs/ 目录**：仅在 README 已明显过长、存在多个稳定受众或需要长期维护架构/协议/排障文档时拆分；单一受众的小插件保留一份 README。
- **SECURITY.md**：仅在独立公开仓库需要安全报告渠道，或插件涉及认证、上传、浏览器、远程资源等显著安全边界时创建。
- **PRIVACY.md**：仅在插件采集、持久化或向外发送个人数据，且 README 无法简洁披露时创建。
- **CONTRIBUTING.md**：仅在独立仓库确实接受外部贡献并已有明确流程时创建。
- **examples/**：仅在编程式 Service/API 调用或复杂配置无法用一小段 README 示例讲清时创建。
- 其他指南、设计说明和迁移文档只在受众、长期维护价值和内容范围明确时创建。

## README 最小内容

README 应精简且可操作，至少覆盖以下适用章节：

1. **插件简介**：解决什么问题、适用范围。
2. **安装与启用**：插件目录、必要依赖和启用方式；不虚构不存在的安装命令。
3. **配置**：列出用户需要修改的字段、默认行为和敏感值的安全配置方式；无配置时明确写“无需额外配置”。
4. **使用方法**：给出真实命令、触发条件或调用示例。
5. **组件与行为**：只写实际提供的组件，并说明组件差异。
6. **限制、安全与数据边界**：平台、聊天类型、权限、外部服务、最低核心版本及已知限制；涉及网络、文件、数据库、主动发送/删除/发布或用户数据时，说明副作用、存储位置和删除方式。
7. **开发与验证**：独立发布或面向贡献者时，给出实际 lint、`mpdt plugin check`、`verify_plugin.py` 和 pytest 命令。
8. **许可证与维护者**：独立分发插件说明许可证和维护者；主仓插件可引用主仓许可证。

按组件类型补充不同信息：

| 组件 | README 应说明的差异信息 |
|---|---|
| Command | 命令前缀、完整语法、参数、权限、聊天范围和示例 |
| EventHandler | 监听事件、触发条件、作用范围、是否拦截消息及副作用 |
| Tool | LLM 可查询的信息、输入参数、返回内容和可用范围 |
| Action | LLM 会执行的副作用、确认或权限要求、`associated_types` 所代表的场景 |
| Agent / Chatter | 负责的对话流程、触发方式、可用工具或终止行为 |
| Config | 字段、类型、默认值、是否必填、热重载行为；密钥只说明配置位置，不给真实值 |
| Service | 完整组件签名、面向其他插件的稳定方法和状态持久化约束 |
| Router | 路径、方法、请求/响应、鉴权和副作用 |
| Adapter | 支持的平台、协议边界、连接配置和消息能力 |

无某类组件时不要保留对应空章节。

## 与 manifest 和实现保持一致

每次开发结束都人工核对文档、`manifest.json` 和代码：

- README 中的插件名、版本（若展示）、最低核心版本、入口、依赖与 `manifest.json` 一致。
- README 和 API 文档只列 `configs`、`get_components()` 实际注册的组件；组件名称和完整签名一致。
- 命令语法、权限、平台、聊天类型、事件类型、配置字段与默认值来自实现，不凭模板猜测。
- `manifest.include` 与实际注册组件一一对应；依赖签名与组件 `dependencies` 一致。
- `manifest.name` 与插件类 `plugin_name` 一致，`manifest.version` 与插件代码及其他版本源一致。
- 删除或重命名组件时同步移除旧文档、旧示例和旧 manifest 项，避免“兼容说明”变成重复文档。

## CHANGELOG 写法

只有满足“条件创建”时才维护 CHANGELOG。推荐使用简化的 Keep a Changelog 结构：

```markdown
# Changelog

## [Unreleased]

### Added
- ...

### Changed
- ...

### Fixed
- ...

### Security
- ...

## [1.2.0] - 2026-07-28
- ...
```

- `Unreleased` 只记录已经完成但尚未发布、且用户可感知的变化；没有内容时不创建空分类。
- 发布时把内容归入带日期的版本；按需使用 Added/Changed/Fixed/Security/Deprecated/Removed。
- CHANGELOG 面向用户，不把 commit 标题逐条复制进去，也不记录纯格式化和无行为变化的内部重构。
- 尚未确定发布版本时不写虚假版本号或发布日期。

## 禁止事项

- 禁止创建空 README、空 CHANGELOG、空 LICENSE、空 API 文档或只有标题/TODO 的占位文件。
- 禁止复制同一说明到多个文件；选择一个权威位置，其他位置只做必要链接。
- 禁止把临时计划、逐步操作日志、调试记录、Agent 思考过程或验收过程写入长期插件文档。
- 禁止记录尚未实现的能力为既有功能；未来设想必须由用户明确要求，并与当前能力清楚区分。
- 禁止在文档中写真实密钥、令牌、私有地址或用户环境中的绝对路径。
